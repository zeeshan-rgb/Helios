# JARVIS code audit - 2026-06-24

_Multi-agent deep audit. 99 raised -> 89 confirmed, 4 uncertain. Health: **needs-significant-work**._

## Executive summary

JARVIS is a capable, feature-rich local assistant, but the audit reveals it is in a transitional state that has left real holes. The dominant theme is the incomplete migration from the retired in-process pyautogui computer-use server to the external cua-driver: the safety mechanisms that used to live in that retired file (panic soft-stop via abort.flag, single-driver screen lock, "defer while user is active") are now DEAD with no live replacement, so panic can no longer stop an in-flight screen action and parallel agents can fight over the mouse/keyboard with nothing serializing them. The second dominant theme is the permission/autonomy model: it auto-allows a complete read-then-exfiltrate primitive (broad Read + unconditional WebFetch), auto-allows file writes to code-execution targets (.bashrc/PowerShell profile, and critically the app's own custom_tools/ dir which is exec'd at startup), and blanket-allows the entire mcp__computer__ control namespace — all reachable via prompt injection from web/RAG/Telegram content. Third, concurrency correctness is weak throughout: cross-thread pywebview GUI calls from HTTP workers, several check-then-act races on concurrency caps, orphaned claude -p process trees on quit/panic, and a clean shutdown that closes nothing (sockets, child processes, HTTP server all leaked). Fourth, a cluster of correctness bugs: an XSS hole in the dashboard renderer, the RAG index-clear that silently wipes sibling folders via an unbounded LIKE prefix, the battery sentinel read as signed (firing "Battery at -1%" alerts on desktops), and the Windows argv length limit silently dropping memory write-back on the longest conversations. None of these are architectural dead-ends — the core design (claude -p routing, SSE dashboard, SQLite, MCP) is sound — but the security gating, the post-cua-driver computer-use safety layer, and process/thread lifecycle need concentrated work before this is trustworthy as an always-on autonomous agent.

## Revamp assessment

No subsystem needs a from-scratch rewrite — the core architecture (claude -p routing, ThreadingHTTPServer+SSE dashboard, SQLite/WAL, MCP tools, side-agent/mission fan-out) is sound and well-factored. The work is targeted hardening, with two areas warranting a focused re-implementation (not a rewrite):

1) Computer-use safety layer (re-implement, ~1-2 days, high benefit). The abort/soft-stop and single-driver screen-lock semantics were tied to the now-retired pyautogui server and are dead against cua-driver. Rather than reviving mcp/computer_use_server.py, build a small fresh layer in the LIVE path: a PreToolUse-hook check on mcp__computer__* that honors both logs/abort.flag (panic stop) and an app-maintained lock file (serialize concurrent agents). Cost is low; benefit is restoring the actual safety guarantees of an assistant that drives mouse/keyboard — this is the single highest-value piece of real work.

2) Permission/autonomy policy (rework the model, ~1-2 days, critical benefit). The current allow-by-default-with-denylist approach is structurally fragile (XSS-adjacent string matching, letter-boundary verb detection, narrow _SENSITIVE regex) and has produced multiple confirmed bypasses. Flip to allowlist-by-default for outbound/destructive/control surfaces (WebFetch, Composio sends, mcp__computer__*, capability-changing mcp__jarvis__*) and add the code-dir / shell-init write protections. This is a policy-layer rework, not a rewrite — the hook plumbing is fine.

Everything else is point fixes: concurrency caps need atomic claims (not new infra), process lifecycle needs a registry + a real quit_app teardown, the RAG clear/query needs boundary-safe SQL and (only if the index grows past a few thousand chunks) cached float32/numpy scoring. The RAG O(n) Python cosine scan is explicitly fine at current single-user scale — do NOT revamp it now; the boundary-collision delete bug is the urgent part, not the perf. The duplicated claude -p spawn/parse across brain/side_agent/mission_agent should be consolidated into the existing claude_cli.py wrapper to stop drift, but that is cleanup, not a revamp.

## All confirmed findings


### HIGH

- **Background mission workers (wait=false) are untracked and orphaned on panic/parent death** - `C:/Users/Tim/jarvis/jarvis/mission_agent.py`:257-260 _(agents-missions/resource-leak)_  
  spawn_worker(wait=false) calls `threading.Thread(target=execute, args=(run_id,), ...).start()` with NO `register` callback. execute() then spawns a `claude -p` subprocess via subprocess.Popen (line 182) but never registers that Popen with anything panic can reach. The whole spawn_worker call runs inside the MCP server process (mcp/jarvis_server.py spawn_agent at line 225), which is itself a child of the spawning agent's `claude -p` process tree. Consequences: (1) MissionManager._procs only holds the top-level SUPERVISOR proc; kill_tree on panic walks the supervisor's process tree via taskkill /T, but a wait=false worker launched from a DEEPER agent's MCP server is in THAT agent's subtree — if that intermediate agent already exited (the spawner returned and its claude -p turn ended) the daemon thread + its worker subprocess become orphaned with no parent draining its pipes or killing it. (2) Even within a live tree, the worker Popen is never added to any registry, so it depends entirely on OS process-tree kill, which fails once the linking parent dies. This leaks live `claude -p` processes that keep consuming the user's Claude subscription and screen lock.  
  -> Track every worker Popen in a process-global registry (e.g. a module-level set guarded by a lock in mission_agent, keyed by mission_id) and have MissionManager.panic() / a kill-by-mission helper iterate it, in addition to kill_tree on the supervisor. For wait=false, pass a register callback to execute() that records the proc in that registry and discards it in execute()'s finally. Also persist enough to let the app reap orphans by mission_id on shutdown.
- **pywebview window methods invoked from HTTP worker threads (cross-thread GUI calls)** - `C:/Users/Tim/jarvis/jarvis/app.py`:80-118, 180-184 _(core-lifecycle/concurrency)_  
  The server is a ThreadingHTTPServer (server.py do_POST runs on a per-request worker thread). The routes /orb/toggle, /summon, /window/minimize, /window/close call the callbacks wired in main() (toggle=lambda: _show_dashboard(...), summon=lambda: _show_dashboard(True), minimize=_minimize_dashboard, close=lambda: _show_dashboard(False)). Those callbacks invoke pywebview methods on the worker thread: win.show(), win.hide(), win.restore(), win.minimize(), and win.evaluate_js() in _show_dashboard/_minimize_dashboard. pywebview + WebView2 require window manipulation and JS evaluation to occur on the GUI/main thread (the one that called webview.start()). Calling these from an arbitrary HTTP worker thread is unsupported and on Windows/WebView2 can deadlock, no-op silently, or raise (the surrounding try/except just logs and swallows). Because the orb's only way to open the dashboard is POST /orb/toggle, this is the primary user path, so the symptom is intermittent: clicking the orb sometimes fails to show the window. The brain's on_screen_action also pushes _minimize_window onto a fresh daemon thread (brain.py:298), but that one uses raw ctypes ShowWindow which is thread-safe; the pywebview-based path is the unsafe one.  
  -> Marshal these calls onto pywebview's GUI thread instead of running them inline on the HTTP worker. Use a thread-safe mechanism (e.g. a queue drained by a window.events.shown / timer on the GUI thread, or pywebview's own helper) so toggle/summon/minimize/close enqueue a request and the GUI thread performs win.show()/minimize()/restore()/evaluate_js(). At minimum, route all four callbacks through a single dispatcher that posts to the main thread.
- **index_folder/clear_chunks deletes sibling folders due to unbounded LIKE-prefix match** - `C:/Users/Tim/jarvis/jarvis/db.py`:129-138 (and mcp/jarvis_server.py:322) _(memory-rag-db/bug)_  
  clear_chunks(source) deletes WHERE source LIKE source||'%'. add_chunk stores each chunk's source as the absolute FILE path str(p). index_folder calls db.clear_chunks(str(base)) (the FOLDER path) before re-indexing. Because the match is a bare prefix with no path-separator boundary, indexing C:\\docs will also wipe every chunk previously indexed under C:\\docs2, C:\\docs-old, C:\\documents, etc., since 'C:\\docs' is a literal prefix of all of them. The user silently loses an unrelated index. The same boundary bug affects any source that is a prefix of another.  
  -> Match on a path-boundary, e.g. delete WHERE source = base OR source LIKE base+sep+'%' (sep = os.sep), or store/clear by a normalized base column. At minimum append the separator: clear_chunks(str(base) + os.sep) and also handle the exact-base row.
- **Battery percent read as signed c_byte: 255 'unknown' sentinel becomes -1, defeating the unknown-battery guard and false-firing the low-battery alert** - `C:/Users/Tim/jarvis/jarvis/scheduler.py`:29-36, 136-138 _(periphery/bug)_  
  SYSTEM_POWER_STATUS.pct is declared as ctypes.c_byte (SIGNED). Windows writes 255 (0xFF) into BatteryLifePercent when the level is unknown / there is no battery. Read through a signed c_byte, 0xFF is interpreted as -1, not 255. The whole design of _battery() and _observe() relies on the value being literally 255 to mean 'unknown': the docstring says it returns 255 'so the battery alert can't false-fire', and _observe() guards with `if pct < 255 and not charging and pct <= battery_pct`. Because pct is actually -1 in the unknown case, `-1 < 255` is True and `-1 <= 20` is True, so on a desktop with no battery (or any moment Windows reports unknown) the alert fires with the nonsensical text 'Battery at -1% and unplugged, sir'. The ac field has the same signed-byte problem: AC unknown (255) reads as -1 so `s.ac == 1` is correctly False, which makes charging=False and lets the false alert through. Note the explicit `return 255, True` fallback in the except branch never matches the `pct < 255` test either way, but the real-call path is the bug.  
  -> Declare ac, flag, pct, r as ctypes.c_ubyte (unsigned) instead of c_byte so 255 reads as 255. Then `pct < 255` and the existing logic behave as documented. Alternatively keep c_byte but normalize: `pct = s.pct & 0xFF` before comparing, and treat 255 as unknown.
- **Attribute-injection XSS via link href in render() (esc() does not escape quotes)** - `C:/Users/Tim/jarvis/jarvis/ui/app.js`:24-40 _(ui-frontend/security)_  
  esc() (line 24-26) only escapes &, <, > — NOT double-quote (") or single-quote ('). render() then interpolates a URL straight into an href attribute delimited by double quotes: the markdown-link rule `html.replace(/\[([^\]]+)\]\((https?:\/\/[^\s)]+)\)/g, '<a href="$2" class="lnk">$1</a>')` (line 34) and the bare-URL rule `return \`${pre}<a href="${u}" class="lnk">${u}</a>\`` (line 37-40). The URL capture group `[^\s)]+` / `[^\s<>"'\`]+` permits a literal `"`. Because the prior esc() pass leaves `"` intact, a model/tool response containing e.g. `[x](https://a.com/"onfocus=alert(1)autofocus="x)` produces `<a href="https://a.com/"onfocus=alert(1)autofocus="x" class="lnk">` — breaking out of the href and injecting active HTML attributes (event handlers) that execute JS. This content is fully attacker/model-controllable: brain.py emits raw `delta["text"]` from `claude -p` as `token` events (brain.py:269) and the final `done` text (brain.py:233), and app.js feeds both directly through render()→innerHTML (app.js:97, 110, 115, and mission render(m.result) at line 273). A web page the model is asked to summarize, a tool result, or a prompt-injected instruction can therefore run arbitrary JS inside the privileged dashboard, which holds the auth TOKEN and can call every server endpoint (/open, /panic, /message, /window/*). This is a full dashboard-context compromise.  
  -> Escape quotes in esc() so it is safe for attribute contexts: `return s.replace(/[&<>"']/g, c => ({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;',"'":'&#39;'}[c]))`. Additionally, encodeURI/validate the captured URL before placing it in href and reject non-http(s) schemes. Note esc() runs once at the top of render(), so escaping quotes there covers both the href value and link label.
